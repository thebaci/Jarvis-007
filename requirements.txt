# fastapi + starlette: SINCE 0.59.19 THEY ARE NO LONGER PINNED AS A PAIR. fastapi 0.141.1 declares `starlette>=0.46.0`
# with NO upper bound, unlike fastapi 0.115.0 (which needed starlette<0.39, so changing one meant changing
# both or pip's resolver broke). Since nobody caps it any more, THIS FILE ITSELF must pin
# starlette to a specific number: left open, every fresh install lands on a different 1.x release,
# and one day on one with a regression, and nobody knows why.
#
# claude-agent-sdk 0.2.116 does not constrain starlette at all (it only needs anyio, mcp,
# sniffio); mcp 1.30 only needs starlette>=0.27. Rechecked with pip install --dry-run when upgrading:
# both work with starlette 1.6.0 without conflict.
#
# WHY UPGRADE (issue #267): starlette 0.38.6 has 7 advisories. Each was checked for whether Jarvis 007 touches
# it, and two really do:
#   - PYSEC-2026-1943 (fixed in 0.40.0): non-file form fields are buffered with NO limit, so a few
#     parallel requests eat all the RAM. Jarvis 007 accepts Form(...) on many endpoints, and
#     Jarvis 007's own code CANNOT patch this. This is the main reason for this upgrade.
#   - PYSEC-2026-2281 (fixed in 1.1.0) WINDOWS ONLY: StaticFiles hitting a UNC path leaks NTLM.
#     Jarvis 007 mounts /static, so a Windows machine exposed to the Internet is really affected.
#   - PYSEC-2026-1941 (fixed in 0.47.2) lightly affected: a large upload clogs the event loop. Slow, not leaky.
#   - PYSEC-2026-161 (fixed in 1.0.1) REALLY affected and serious (url.path can be bent by the Host header, bypassing
#     the login gate entirely) but Jarvis 007 already PATCHED it itself in 0.59.16 (duong_dan_router + host_hop_le). That
#     patch STAYS as is after the upgrade: the fence reads scope["path"], which is correct on every version.
#   - PYSEC-2026-248 / 2280 / 249: not affected (248 gets a 400 from uvicorn before reaching the app, tested
#     with a raw socket; the HTTPEndpoint class is not used; max_fields/max_part_size are not set).
#
# DEBT LEFT AFTER THE UPGRADE: 6 `@app.on_event("startup")` and 1 "shutdown" in main.py are a
# removed API. Starlette 1.x deletes on_startup/on_shutdown, fastapi 0.141 still helps with its own
# list so it still RUNS, only raising a DeprecationWarning. Moving to lifespan is a separate job:
# it merges 7 functions into one place and the order they run in is the easiest part to get wrong.
